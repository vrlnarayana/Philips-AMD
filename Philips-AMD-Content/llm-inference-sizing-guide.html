How inference actually spends the GPU

Every request runs in two phases with opposite bottlenecks. Knowing which one limits you tells you which GPU spec matters.

Prefill — reads your prompt

Summarisethiscontract…2,000 tokens

All prompt tokens are processed in one parallel pass. That is a big matrix multiply, so it is compute-bound: TFLOPS decide how fast it goes. It sets time to first token (TTFT).

Cost ≈ 2 × active parameters × prompt tokens FLOPs. Long RAG prompts make this phase dominate.

Decode — writes the answer

Thecontractrequiresnotice

One token per step, per user. Each step must stream the model weights and that user's KV cache from memory, so it is memory-bandwidth-bound: GB/s decide speed per user.

Batching is the trick: one weight read serves many users at once, so total throughput rises almost linearly with batch until compute or KV memory runs out.

The KV cache is what limits concurrency

For every token in every live conversation the engine stores a key and value vector per layer. Per token that costs 2 × layers × kv_heads × head_dim × bytes. Llama 3.1 8B needs 128 KB per token in FP16, so one 32k-token conversation holds 4 GB. Whatever memory is left after the weights decides how many users fit at once — that is the teal part of the bar above.

Architectural tricks shrink this: grouped-query attention (fewer KV heads), DeepSeek's multi-head latent attention (a compressed 576-value cache per layer), sliding-window layers (gpt-oss) and hybrid linear attention (Qwen3-Next keeps full KV on only 12 of 48 layers). FP8 KV cache halves it on any model.

Deploying a model for inference

A production path that works for anything from one L4 to a rack of H200s.

  1. Pick the model for the task, not the leaderboard.

    Start from the smallest model that passes your own eval set. Check licence, context length and tool-calling support. MoE models (e.g. Qwen3-30B-A3B, gpt-oss-120b) give big-model quality at small-model speed if you have the memory.

  2. Choose the precision your GPU runs natively.

    FP8 on Ada/Hopper, NVFP4 on Blackwell, INT4 AWQ/GPTQ or INT8 on Ampere. Prefer an official pre-quantized checkpoint; otherwise quantize with LLM Compressor, ModelOpt or AutoAWQ and re-run your eval.

  3. Choose an engine.

    vLLM — widest model and quant support, OpenAI-compatible server. SGLang — very fast for agents, structured output and prefix-heavy traffic. TensorRT-LLM — highest peak on NVIDIA, more build work (packaged as NVIDIA NIM). llama.cpp / Ollama — single user, laptops, CPU+GPU offload.

  4. Size the hardware.

    Use the lab above: weights + overhead must fit with room for KV cache for your concurrent users. If it barely fits, you will get very low concurrency — go one GPU tier up or one quant step down.

  5. Launch the server.

    Set tensor parallelism to the number of GPUs, cap context length to what you actually need (it frees KV memory), turn on prefix caching and FP8 KV where supported. Commands below.

  6. Benchmark with your traffic shape.

    Replay realistic prompt/output lengths at rising request rates. Record TTFT p50/p95, inter-token latency and throughput; stop at the rate where p95 breaks your SLA. That rate — not peak tokens/s — is your capacity.

  7. Operate.

    Put a gateway in front (auth, rate limits, routing). Scrape the engine's Prometheus metrics (queue length, KV cache usage). Autoscale on queue depth or KV usage, not CPU. Pin model revisions.

Quantization: every format, and when to use it

Quantization stores numbers in fewer bits. Fewer bytes per weight means a bigger model fits and each decode step reads less memory, so it runs faster. The risk is accuracy loss, which is usually small at 8 bits and model-dependent at 4 bits.

Reading the names: W4A16 = 4-bit weights, 16-bit activations (saves memory, math still in BF16). W8A8 = both 8-bit (also doubles math throughput on supporting hardware). Group size (e.g. g128) = how many weights share one scale factor; smaller groups are more accurate but slightly larger.

Mixture-of-Experts, and what "A3B" means

An MoE layer replaces one big feed-forward block with many smaller "experts". A router sends each token to only a few of them. So the model is large on disk but cheap per token.

Watch the router

Why batch size changes MoE economics

Share of experts that must be read from memory in one decode step, per layer, assuming even routing.

At batch 1 an MoE reads only its active experts, so it decodes like a small dense model. As the batch grows, different tokens pick different experts, and soon almost every expert is read each step. At that point the step is as memory-heavy as a dense model of the full size — but compute per token still stays small, so MoE keeps a big throughput advantage.

Decode any model name

The rule of thumb

Memory scales with total parameters. Speed scales with active parameters. 30B-A3B means 30 billion total and about 3 billion active per token — you must hold all 30B in VRAM, but each token costs roughly what a 3B model costs. A4B, A12B, A22B follow the same pattern. Some families use other conventions: Mixtral 8x7B (8 experts of ~7B; really 47B total, 13B active because attention is shared), Llama 4 17B-16E (17B active, 16 experts), and gpt-oss just states total size (120b has 5.1B active).

MoE is the best fit when memory is plentiful but bandwidth or compute is not — for example a 96 GB RTX PRO 6000 or an H200 serving many users. It is a poor fit for small-VRAM cards, because a model that runs like a 3B still needs the memory of a 30B.

Glossary

TTFT
Time to first token. Queueing + prefill time. What users perceive as "responsiveness".
TPOT / ITL
Time per output token / inter-token latency. The inverse is tokens/s per user.
Throughput vs goodput
Throughput counts all tokens produced. Goodput counts only requests that met your latency SLA — the number to plan capacity with.
Continuous batching
New requests join the running batch at every decode step instead of waiting for a batch to finish. The main reason modern engines serve many users per GPU.
PagedAttention
vLLM's technique of storing the KV cache in fixed-size pages, like virtual memory, so almost no memory is wasted on fragmentation.
Prefix caching
Reuses the KV cache of a shared prompt prefix (system prompt, RAG context, chat history) across requests, skipping repeat prefill.
Chunked prefill
Splits long prompts into chunks interleaved with decode steps so one long prompt doesn't freeze everyone else's streaming.
Speculative decoding
A small draft model (or EAGLE heads, or MTP layers as in DeepSeek) proposes several tokens; the big model verifies them in one step. Speeds up low-batch decode 1.5–3×.
Tensor parallel (TP)
Splits each layer across GPUs. Needs fast interconnect (NVLink). Adds memory and bandwidth; the usual way to fit a big model.
Pipeline parallel (PP)
Puts different layers on different GPUs or nodes. Tolerates slower links; used across nodes.
Expert parallel (EP)
Places different MoE experts on different GPUs. Standard for DeepSeek/Kimi-scale models.
Disaggregated serving
Runs prefill and decode on separate GPU pools so each can be sized and batched for its own bottleneck.
max-model-len
The longest context the engine will accept. Lowering it frees KV memory and raises concurrency.
max-num-seqs
Maximum requests in one batch. Caps concurrency even if memory would allow more.
